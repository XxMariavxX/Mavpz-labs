# Специфікація процесу: UC-5 «Оформити замовлення» та UC-6 «Обробити підтвердження оплати»

## 1. Намір та межі (Scope)

- **Намір**: описати бізнес-процес оформлення замовлення (UC-5/UC-6) однією Activity-діаграмою з Swimlanes, узгодженою з ERD (lab1), EARS/UC (lab2) і Sequence (lab3).
- **Вхідні умови**: авторизований користувач з позиціями у кошику, ініціює `submitCheckout(cartItems)`. Резерв `Hold` може бути створений при додаванні в кошик (REQ-ED-7).
- **Вихідні умови**: `Order` переходить у `paid` (залишок списано через `commitStockDeduction`) АБО у `cancelled` (резерв знято через `releaseStockReservation`). Сторона клієнта отримує сповіщення.
- **Out of Scope**: реєстрація, повернення коштів (Refund), адміністрування каталогу.

## 2. Ролі та компоненти

1. **Користувач / UI (Client)**: ініціює оформлення, проходить автентифікацію, переходимо на оплату, отримує сповіщення, обирає «Повторити оплату».
2. **Система (OrderService / InventoryService / PaymentService)**: перевірка `User.status`, перевірка наявності `Order` у статусі `created` (REQ-SD-1), перевірка/створення `Hold` (REQ-ED-7, REQ-UB-5), створення `Order`/`OrderItem`, ініціалізація платежу, оновлення статусів, `Fork/Join` при `PAID`, списання/звільнення резерву.
3. **Платіжний шлюз (PaymentGateway)**: платіжна сесія, вебхук `PAID`/`FAILED`, час життя сесії (TTL).

## 3. Кроки процесу

1. `submitCheckout` → перевірка `User`: якщо не автентифіковано (`AuthRequired`) — редирект на автентифікацію (REQ-UW-3); якщо `User.status = banned` (`UserBlocked`) — показ «оформлення недоступне» (REQ-SD-2); інакше — далі.
2. Перевірка наявності `Order` у статусі `created` — блокування повторного списання (REQ-SD-1).
3. Цикл по позиціях: перевірка активного `Hold`; якщо відсутній/прострочений — перевірка `stock_quantity`, за наявності створюється новий `Hold` на 30 хв (REQ-UB-5, REQ-ED-7, REQ-UB-9).
4. Якщо є позиція з недостатнім залишком — скасування усіх `Hold`, помилка, `Order` не створюється (REQ-UW-1, REQ-UW-6).
5. Створення `Order` (`created`) та `OrderItem`, розрахунок суми.
6. Ініціалізація платежу, редирект на шлюз.
7. За `PAID` — `updateOrderStatus(paid)`, паралельно (`Fork/Join`) `commitStockDeduction` та сповіщення (REQ-ED-2).
8. За `FAILED` — `updateOrderStatus(cancelled)`, `releaseStockReservation`, пропозиція повторити оплату (REQ-UW-2).
9. За `TTL` — фоновий/сесійний таймаут, `expireHold`, `updateOrderStatus(cancelled)`, `releaseStockReservation`; сесію закрито без повідомлення про помилку оплати (REQ-SD-3).

## 4. Критерії прийняття

-  Є одна Activity-діаграма з Swimlanes (`Client`, `System`, `Gateway`).
-  Наявні розгалуження та `fork/join` (≥1 кожного).
-  Покрито UC5-S1…S6.
-  Узгодженість із `lab1` (статуси/сутності), `lab2` (UC/REQ), `lab3` (послідовності).
-  Узгодженість процесу: при `Retry` виконується перевірка залишку/hold перед створенням нового `Order`.
-  Діаграма рендериться в Mermaid без помилок.

## 5. Покриття сценаріїв UC-5

| Сценарій | Що покрито |
|---|---|
| UC5-S1 | Перевірка користувача, перевірка наявності `Order`, цикл перевірки hold/залишку, створення `Order` |
| UC5-S2 | Webhook `PAID`, `fork/join`, `commitStockDeduction` |
| UC5-S3 | Webhook `FAILED`, скасування, зняття резерву, `Retry` |
| UC5-S4 | Блокування при `Order` в статусі `created` |
| UC5-S5 | Повторна оплата після помилки з повторною перевіркою залишку |
| UC5-S6 | Недостатній залишок, скасування hold, `Order` не створюється |
