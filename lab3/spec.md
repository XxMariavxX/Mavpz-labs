## Опис та вибір сценарію

*   Сценарії: Деталізація прецедентів UC-5: Оформити замовлення та UC-6: Обробити підтвердження оплати
*   Мета: показати взаємодію клієнта, внутрішніх сервісів платформи та зовнішнього платіжного шлюзу від моменту натискання <Купити> до отримання повідомлення про оплату

## Учасники сценарію:

*   Покупець (User) - авторизований покупець;
*   UI (фронтенд) - клієнтський веб-інтерфейс;
*   OrderService - сервіс управління життєвим циклом замовлень (Order);
*   InventoryService - сервіс контролю залишків та керування тимчасовими резервами;
*   PaymentService - сервіс обробки платежів та взаємодії зі шлюзом;
*   PaymentGateway - зовнішній банківський платіжний шлюз;
*   Storage - сховище доменної моделі (User, Order, OrderItem, Product);

## Кроки сценарію

# Успішний варіант:

1.  Покупець(авторизований користувач) у кошику натискає `<<Оформити замовлення>>`;
2.  UI передає запит у OrderService (submitOrder(userId, cartItems));
3.  OrderService перевіряє користувача (validateUser(userId)): статус User має бути active;
4.  OrderService перевіряє, чи немає вже Order у статусі created для цього кошика;
5.  Цикл перевірки: для кожної позиції товару OrderService запитує у InventoryService перевірку резерву. Резерв створюється під час додавання в кошик (REQ-ED-7). Якщо hold активний, позиція підтверджується. Якщо hold відсутній або прострочений (нова сесія, REQ-UB-5), InventoryService перевіряє залишок і створює новий hold на 30 хв. Результати всіх позицій збираються в циклі;
6.  OrderService зберігає сутність Order у статусі created з order\_number, записує позиції OrderItem та розраховує загальну суму;
7.  OrderService звертається до PaymentService для ініціалізації оплати;
8.  PaymentService створює платіжну сесію у зовнішньому PaymentGateway та отримує посилання на оплату;
9.  UI перенаправляє покупця на захищену сторінку шлюзу, де покупець вводить реквізити та підтверджує платіж;
10.  PaymentGateway асинхронно надсилає вебхук із підтвердженням;
11.  PaymentService сповіщає OrderService про успішну оплату;
12.  OrderService оновлює статус замовлення в сховищі на paid та дає команду InventoryService на остаточне списання зарезервованого залишку;
13.  Покупець отримує сповіщення про успішне оформлення замовлення;

# Альтернативні варіанти:

*   Варіант1: Невистачає продукції на складі (REQ-UW-1, REQ-UW-6):
    1.  Якщо під час перевірки виявляється, що товару немає або його недостатньо, InventoryService повертає помилку InsufficientStock;
    2.  OrderService скасовує тимчасові броні для інших позицій цього кошика. Замовлення не створюється;
    3.  UI виводить сповіщення: `<<Товару немає в наявності>>`;
*   Варіант2: Помилка оплати (REQ-UW-2):
    1.  Якщо платіжний шлюз повертає помилку (status = FAILED), PaymentService повідомляє OrderService;
    2.  OrderService оновлює статус замовлення в сховищі на cancelled;
    3.  OrderService надсилає команду в InventoryService зняти бронь (releaseStockReservation(orderId)), повертаючи товар у вільний продаж;
    4.  UI показує повідомлення про збій списання та дію `<<Повторити оплату>>` (яка ініціює новий Order);
*   Варіант3: Таймаут оплати та закінчення резерву у 30 хв (REQ-SD-3, REQ-UW-7):
    1.  Якщо покупець закрив сторінку оплати або не ввів реквізити протягом 30 хвилин, платіжна сесія вважається простроченою;
    2.  Фоновий таймер сервісу переводить замовлення зі статусу created у cancelled;
    3.  InventoryService автоматично анулює тимчасовий резерв товару на складі;
*   Варіант4: Блокування повторного списання (REQ-SD-1, UC5-S4):
    1.  Якщо користувач повторно натискає кнопку оплати або надсилає повторний запит, поки перша операція ще обробляється шлюзом (статус created), система блокує створення другого запиту;
    2.  UI виводить індикатор: «Оплата вже обробляється, зачекайте»;
*   Варіант5: Неавторизований користувач (REQ-UW-3, UC-Auth-S1):
    1.  Якщо користувач не авторизований, OrderService повертає помилку AuthRequired;
    2.  UI перенаправляє користувача на екран автентифікації;
*   Варіант6: Заблокований користувач (REQ-SD-2):
    1.  Якщо статус User має значення banned або inactive (User.status != 'active'), OrderService відхиляє оформлення;
    2.  UI повідомляє: «Оформлення недоступне»;

## Покриття сценаріїв UC-5 і UC-6

Діаграми (README.md) побудовано на кожен сценарій UC-5 з Завдання 2:

| Сценарій | Діаграма | Кроки / варіанти |
|---|---|---|
| UC5-S1 Успішне створення | 1 | 1–9, Варіанти 1, 5, 6 |
| UC5-S2 Успішна оплата | 2 | 10–13 (PAID) |
| UC5-S3 Помилка оплати | 3 | Варіант 2, Варіант 3 (TTL) |
| UC5-S4 Блокування повтору | 4 | Варіант 4 |
| UC5-S5 Повторна оплата | 5 | Варіант 2 → новий Order |
| UC5-S6 Недостатній залишок | 6 | Варіант 1 (rejection на оформленні) |

**Обґрунтування щодо UC-6 «Обробити підтвердження оплати»:** окремої діаграми немає, бо UC-6 не має власних сценаріїв у Завданні 2. Його логіка (PAID / FAILED) є частиною UC5-S2 і UC5-S3, тому деталізовано там: діаграма 2 для PAID, діаграма 3 для FAILED та TTL.
