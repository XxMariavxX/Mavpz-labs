# ADR 0001: Компонентна архітектура з єдиним шаром Data Access

## Status

прийнято

## Context and Problem Statement

Потрібно описати архітектуру платформи компонентами, інтерфейсами та залежностями, узгоджену з ERD, UC, Sequence і процесом. Потрібно вирішити, чи об'єднувати сервіси замовлення/залишку/оплати та як організувати доступ до БД.

## Decision Drivers

- Наскрізна узгодженість lab1 → lab2 → lab3 → lab4 → lab5.
- Чітка межа системи та зовнішні інтеграції.
- Provided/required-інтерфейси визначені явно.

## Considered Options

**A. Один монолітний backend-компонент.**
- Плюси: простіше.
- Мінуси: приховує залежності, важче трасувати до sequence.

**B. Окремі сервіси (Order, Inventory, Payment) + єдиний Data Access + зовнішні інтеграції.**
- Плюси: явні інтерфейси, узгоджено з lab3/lab4, чітка межа системи.
- Мінуси: більше компонентів.

## Decision Outcome

Обрано варіант B. Сервіси розділено, доступ до БД — через єдиний шар Repository; зовнішні інтеграції позначено як System_Ext.

## Consequences

- Кожен компонент трасується до попередніх моделей.
- Зовнішні інтеграції ізольовані за межею системи.
- Зміна БД впливає лише на шар Data Access.
- Негативний наслідок / Компроміс: додавання окремого шару Data Access (Repository Layer) вимагає написання додаткового абстрактного коду для мапінгу сутностей PostgreSQL, що трохи збільшує обсяг коду системи.
